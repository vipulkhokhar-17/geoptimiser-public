# Feature validation guide

How to tell what a feature result is worth, and how to raise that. It covers the three
labels every feature carries, the evidence each level needs, how to write a fixture, and
what cannot be claimed yet.

Related: [DEVELOPMENT_GUIDE.md](DEVELOPMENT_GUIDE.md) (commands, adding a check),
[../validation/GEOPTIMISER_FEATURE_AUDIT.md](../validation/GEOPTIMISER_FEATURE_AUDIT.md)
(the per-feature register), [../validation/VALIDATION_POLICY.md](../validation/VALIDATION_POLICY.md)
(the rules fixtures encode), [../validation/AI_OUTCOME_PROTOCOL.md](../validation/AI_OUTCOME_PROTOCOL.md)
(how AI outcomes would be measured), ADR-0030 and ADR-0031 in [../DECISIONS.md](../DECISIONS.md).

## 1. The three labels

Every feature has three independent labels. They are generated by
`python -m geoptimiser.validation.matrix --write` into
`docs/validation/feature_validation_matrix.csv` and
`src/geoptimiser/validation/feature_levels.json`, and served by `GET /api/v1/catalog`, which
is what the UI's feature catalog and explorer show.

**Implementation level** — does code exist, and does it measure the whole property?

| Level | Meaning |
|---|---|
| IMPLEMENTED | a check measures the property as described |
| PARTIAL | a check runs but measures part of it; the limits say which part |
| PLANNED | catalogued, no check yet; it never appears as pass or fail |
| UNAVAILABLE | needs something the system cannot do (JavaScript rendering, observed AI answers) |
| NOT_VERIFIABLE | cannot be decided from evidence the audit can collect (none today) |

**Validation level** — the highest kind of evidence that the check is right. Levels are
cumulative: a feature at PIPELINE_VALIDATED also meets FIXTURE_VALIDATED.

| Level | Evidence required |
|---|---|
| NOT_TESTED | no check, or no test |
| UNIT_TESTED | unit tests only (`tests/features/`) |
| FIXTURE_VALIDATED | at least one pre-declared expectation in a synthetic fixture, met by the crawl → extract → features harness |
| PIPELINE_VALIDATED | those expectations also met when the fixture is run through `AuditService` and the HTTP API (`tests/validation/test_app_pipeline.py`) |
| REAL_PAGE_VALIDATED | precision and recall measured on a labelled corpus of real pages — **no feature is here; no such corpus exists** |
| OUTCOME_VALIDATED | a measured effect on AI-search visibility — **no feature is here; no outcome data exists** |

**Disposition** — a judgment about what to do with the feature, written in
`src/geoptimiser/validation/judgments.py` with its reasons.

| Disposition | Meaning |
|---|---|
| RETAIN | well founded and working; keep as is |
| REVISE | keep, but the method, threshold or wording needs work (the reason is recorded) |
| INFORMATIONAL_ONLY | useful context, not evidence of quality; unscored or a notice |
| REMOVE | should be retired (none today) |
| INVESTIGATE | precision unknown or unimplemented; do not rely on it yet |

Current counts (2026-11-08): implementation 41 / 41 / 36 / 2 / 0; validation 38 not tested,
47 unit-tested, 35 pipeline-validated, 0 real-page, 0 outcome; disposition 24 retain, 15
revise, 32 informational, 0 remove, 49 investigate. Regenerate rather than trusting these.

## 2. What a result can and cannot tell you

* A `pass` or `fail` says what the HTML **as fetched** contains. JavaScript is not run.
* `not_measured` means the evidence was missing or incomplete (a truncated body, a rate
  limit, a crawl that did not reach the target). It is never a defect.
* `not_applicable` means the property does not apply to this page.
* A feature at UNIT_TESTED or FIXTURE_VALIDATED is right on **constructed cases**. That is
  not accuracy on real websites.
* Nothing in the catalog is shown to improve AI citations or visibility. Claims of that kind
  are in the catalog only as "claimed outcome", labelled with their strength (standard,
  vendor documentation, plausible mechanism, unvalidated).

## 3. Raising a feature's validation level

### To UNIT_TESTED

Write tests in `tests/features/test_checks_<area>.py` using the builders in
`tests/features/builders.py` (`page`, `audit`, `run`, `status_of`). Cover pass, fail,
malformed input, missing evidence (`not_measured`) and the not-applicable case.

### To FIXTURE_VALIDATED and PIPELINE_VALIDATED

Add a fixture directory `tests/validation/fixtures/<id>/spec.json`. **Write the
expectations before the first run** and do not edit them to match the output; if the code
disagrees, either the code is wrong or the policy is, and the policy change needs a
reason in the work log.

```json
{
  "spec_version": 1,
  "id": "k1_transport_security",
  "title": "HTTPS with and without a usable HSTS policy (F110)",
  "description": "Why the fixture exists and what was decided before running it.",
  "kind": "isolated",
  "crawl": {"max_pages": 25, "max_depth": 2},
  "site": {
    "/robots.txt": {"text": "User-agent: *\nAllow: /\n", "content_type": "text/plain"},
    "/": {"text": "<!doctype html>…", "headers": {"Strict-Transport-Security": "max-age=31536000"}},
    "/no-hsts": {"text": "<!doctype html>…"}
  },
  "expect": {
    "pages": {
      "/":        {"F110": {"status": "pass", "explanation_contains": ["max-age=31536000"]}},
      "/no-hsts": {"F110": {"status": "fail"}}
    }
  }
}
```

What a spec can declare (`src/geoptimiser/validation/spec.py`):

| Part | Fields |
|---|---|
| route | `status`, `headers`, `content_type`, `text` or `file`, `behavior` (`normal`, `drop`, `hang`) |
| `crawl` | `max_pages`, `max_depth`, `max_response_bytes`, `request_timeout_seconds`, `respect_robots` |
| page or site expectation | `status`, `explanation_contains`, `explanation_excludes`, `limitation_contains`, `severity`, `note` |
| `findings` | `present`, `absent`, `severity`, `text_contains`, `text_excludes` |
| `scores` | `overall` and `categories` (`reportable`, `score`, `feature_coverage`), `contributing`, `not_contributing` |
| recommendations | `recommendation_includes`, `recommendation_excludes` |

Run it:

```bash
python -m geoptimiser.validation --fixtures tests/validation/fixtures --only k1_transport_security
python -m pytest tests/validation -q        # also replays every fixture through the app and API
python -m geoptimiser.validation.matrix --write
```

The matrix picks the fixture up automatically: a feature with a met expectation in a
fixture becomes FIXTURE_VALIDATED, and PIPELINE_VALIDATED as long as the same fixture
passes `test_app_pipeline.py`. A fixture that intentionally produces no feature results
(a failed crawl) is listed in `APP_PIPELINE_NO_FEATURES` in
`src/geoptimiser/validation/levels.py`.

### To REAL_PAGE_VALIDATED (not yet possible)

It needs a corpus of real page snapshots, collected with permission, with labels from
people or an independent oracle that does not share the code under test, and enough
positive and negative cases for a confidence interval. The machinery exists:

```bash
python -m geoptimiser.validation.corpus --manifest benchmarks/corpus/manifest.json
```

It reports precision and recall with Wilson intervals, and reports "undefined" rather than
0 when a denominator is empty. The shipped corpus is 14 repository-local pages with labels
from an independent parser, and its manifest says `real_world: false`. That checks the
extractor; it is **not** real-page validation, and the 95 % / 80 % precision targets are not
assessed.

### To OUTCOME_VALIDATED (not yet possible)

It needs a live answer-engine adapter and the controlled before/after protocol in
`docs/validation/AI_OUTCOME_PROTOCOL.md`. Neither exists, so category L features are
unimplemented and no outcome claim is made anywhere.

## 4. Sources and thresholds

`src/geoptimiser/validation/sources.py` lists every external source a feature relies on.
A source is marked **primary** only after its own page (a standard, an RFC, the vendor's
documentation) has been read; S01, S03–S08 and S11–S14 were re-read at the primary source
on 2026-11-01, and S02, S09 and S10 remain secondary. A correction found on re-reading is
recorded (for example S13: Google requires only `name`, `thumbnailUrl` and `uploadDate`
for video structured data). Thresholds and their basis are in the threshold register of
the feature audit; a threshold without a source is labelled a heuristic.

## 5. Review checklist for a feature change

* [ ] The catalog entry says what is measured and what is not (limits).
* [ ] Unknown evidence gives `not_measured`, not `fail` or `pass`.
* [ ] Unit tests and a fixture whose expectations were written first.
* [ ] `@check` version and, if scores can change, `CATALOG_VERSION` bumped.
* [ ] Judgment updated (claim strength, false positives and negatives, disposition).
* [ ] Exports and matrix regenerated; `matrix --check` passes.
* [ ] No claim of an AI-visibility effect.
